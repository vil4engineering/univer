# Почему одной «очереди дел» на процессоре стало мало?

<p class="chapter-deck">

## Интуиция

Представь кухню с одним поваром. Он режет, потом жарит, потом моет. Пока ждёт, пока закипит вода, руки простаивают — а гости уже стучат ложками.

В телефоне то же самое. Сеть отвечает не сразу. Диск читается не мгновенно. Экран должен оставаться живым *сейчас*. Если вся программа — одна жёсткая очередь «сделай A, потом B, потом C», пользователь чувствует зависание задолго до того, как «логика» закончится.

> Concurrency появляется не потому, что «так модно в Swift», а потому что **одна линия исполнения** плохо дружит с ожиданием и с несколькими делами сразу.

На Execution Spine мы уже видели:

> задача → человек → алгоритм → программа → Compiler → Machine Code → CPU → действие в мире

Concurrency живёт на ступени **программа → CPU**: *как* организовать работу, которую машина исполнит, когда шаги больше не укладываются в один спокойный ряд.

---

## Проблема

Последовательный алгоритм прекрасен, пока каждый шаг быстрый и локальный.

Ломается картина, когда:

- шаг **ждёт** внешний мир (сеть, диск, пользователь);
- шаг **долгий** на CPU, а UI должен отвечать;
- железо даёт **несколько ядер**, а состояние программы всё ещё думает, что мир один и общий.

Тогда появляются знакомые симптомы: «крутилка вечность», «нажал — подвисло», «иногда краш только на устройстве». Это не «Swift странный». Это цена наивной модели «всё по порядку в одной голове».

---

## История (коротко)

```text
Один поток мысли в программе
  → «подожди сеть» убивает отзывчивость
  → многоядерные телефоны: хочется делать больше сразу
  → ручные threads / queues / locks — работают, но гонки ловятся поздно
  → современные модели (structured concurrency, isolation) — ответ на ту же боль, не новый спорт
```

Имена механизмов менялись. Боль одна: **организовать работу так, чтобы ожидание и параллель не разрушили смысл программы**.

---

## Как это работает

Два слова, которые путают на интервью:

| Термин | Смысл в этой главе |
|--------|-------------------|
| <a class="eu-term" href="../../../glossary/#glossary-concurrency">Concurrency</a> | *Организация* нескольких дел во времени — чтобы программа продвигалась, пока что-то ждёт или пока дел несколько |
| <a class="eu-term" href="../../../glossary/#glossary-parallelism">Parallelism</a> | *Одновременное* исполнение на нескольких ядрах / единицах железа |

Можно иметь concurrency **без** parallelism: на одном ядре переключаться между делами, пока одно ждёт сеть.  
Parallelism — когда два куска кода реально бегут в один момент на разных ядрах.

Потоки (threads) — **один из механизмов**, не определение concurrency. GCD, `async`/`await`, actors — более поздние ответы на ту же проблему организации. Их API — в следующих материалах хаба, не здесь.

Ментальная модель:

```text
Последовательность  →  «жду» ломает UX
                   →  нужны правила: кто работает, кто ждёт, кто трогает состояние
                   →  потом уже выбирают механизм (queues / tasks / actors)
```

---

## Внутри

Level 3 здесь — дверь, не комната.

На нескольких ядрах **shared mutable state** без правил превращается в гонки: два исполнения правят одни и те же байты. Поэтому позже появятся изоляция, очереди, actors — не как словарь, а как способы сказать: «это состояние трогает только один мир за раз».

Пока достаточно: concurrency решает *организацию*; борьба с гонками — следующая глава боли.

---

## Пример

Псевдокод «плохо» vs «зачем нужна организация» — без Swift Concurrency API:

```text
Плохо (одна жёсткая очередь):
  1. Скачай картинку (ждём сеть…)
  2. Пока ждём — UI мёртв
  3. Покажи картинку

Лучше (идея concurrency):
  1. Запусти загрузку как отдельное дело
  2. UI продолжает слушать жесты
  3. Когда загрузка готова — обнови экран по правилам границы UI
```

Как именно это пишется в Swift (`Task`, MainActor, …) — в [хабе Concurrency](../) и labs. Здесь важна **потребность**, не синтаксис.

## Production

Одна привычка:

> Перед тем как тащить новый механизм concurrency, спроси: **какое ожидание или какое shared state** ломает одну очередь дел?

Если боли нет — не усложняй. Если боль есть — сначала назови её (ожидание / ядра / общее состояние), потом выбирай инструмент.

## Конспект

Коротко со стола.

1. Одна жёсткая очередь дел плохо переживает ожидание и несколько задач.  
2. Concurrency — организация работы во времени.  
3. Parallelism — одновременное исполнение на железе.  
4. Threads — механизм, не определение.  
5. На Execution Spine это вопрос программы для CPU, не отмена позвоночника задача→человек→…→мир.  
6. API и actors — следующие ответы на ту же боль.
